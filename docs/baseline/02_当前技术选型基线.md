# 智能电商客服平台当前技术选型基线

> 2026-09-13 实施修订：本机解释器按用户要求统一为已有 `intelligent-commerce-support-v1`，不再采用下表中的双环境开发方式；安全必要依赖调整见 ADR-0010，实际版本见 `deploy/dev-environment/v1-requirements.lock`。M01 已采用 MySQL 8.4.11、Redis 8.8.2、Milvus 2.6.23、etcd 3.6.14 和 SeaweedFS 4.45，原 MinIO/Milvus 2.5 表格是历史选型，不可再据此安装。下文保留原决策背景；安装请使用当前环境说明。

## 1. 选型结论

本项目取消发布时间限制，采用“当前生产稳定 + KF 兼容优先”的双基线：

1. **平台服务稳定线**：新建的账户、商品、订单、物流、会话、编排、工单、后台和网关采用当前成熟稳定版本。
2. **KF 知识服务兼容线**：V1 保留 KF RAG 已验证的 Python/LangChain/向量检索组合，以独立运行环境隔离；不在首版同时重构业务和升级整条 RAG 依赖链。
3. **V1.5 升级线**：RAG 框架、Milvus、Embedding、Reranker 或解析器升级必须通过 Golden Set、性能测试、资源测试和回滚演练，证明收益后再进入生产。

“当前最合适”不是“全部使用最新版”。刚发布的新主版本、预览版本和不兼容升级不进入 V1。

## 6. 模型与检索选择

| 能力 | V1 选择 | 约束 |
|---|---|---|
| LLM 接口 | 项目内 OpenAI-compatible Port | 业务不绑定具体厂商；本地与云端实现可切换 |
| 默认本地模型 | Qwen3-8B 系列 | 根据 GPU/内存确定量化版本，固定模型 revision 和哈希 |
| Embedding | BGE-M3 | 继承 KF 多语言与稀疏/稠密检索能力 |
| Reranker | BGE-reranker-v2-m3 | 重排模型必须有可关闭的降级开关 |
| 检索 | FAQ + 文档、稀疏 + 稠密、元数据过滤 | 结果统一重排、阈值、引用和拒答 |
| 模型运行 | 独立 Model Provider Adapter | 根据硬件选择本地推理或远程 OpenAI-compatible 服务 |

模型文件不得进入 Git。必须记录来源、许可证、revision、SHA-256、量化方式、硬件需求和 Golden Set 结果。

## 7. 锁定与升级规则

1. Python 平台服务和知识服务分别生成 `uv.lock`，避免新平台 API 依赖与 KF 兼容依赖相互污染。
2. JavaScript 使用 `pnpm-lock.yaml`，CI 强制 `pnpm install --frozen-lockfile`。
3. Docker Compose 禁止 `mysql:8.4`、`redis:7-alpine`、`python:3.12-slim` 等浮动标签；使用精确补丁标签并记录 digest。
4. Dependabot/Renovate 只能创建升级 PR，不能自动合并生产依赖。
5. 补丁升级必须通过 CI、安全扫描和冒烟测试；次版本升级增加契约与 E2E；主版本升级必须写 ADR 并完成回滚演练。
6. RAG 依赖、模型或向量库升级必须在 V1.5 中运行离线回放，至少比较召回率、MRR/NDCG、忠实度、引用准确率、拒答率、P95 延迟、吞吐和资源占用。

## 8. 当前未采用的最新主版本

- Node.js 26 Current：不用，选择 Node.js 24 LTS。
- TypeScript 7：暂不用，选择已经稳定运行数月的 TypeScript 6。
- Pinia 4、Vue Router 5、Vitest 5：发布时间较近，首版选择上一成熟主线。
- LangChain 1.4：发布时间过近；V1 使用 KF 已验证的 1.2 兼容组合。
- PyMilvus 3 / Milvus 3 beta：不进入 V1；避免同时改变检索服务和客户端大版本。

这些组件不是永久禁止。稳定观察、兼容测试和收益评估完成后，可通过 ADR 进入后续版本。

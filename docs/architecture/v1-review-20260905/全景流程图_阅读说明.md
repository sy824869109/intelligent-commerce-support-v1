**17 个步骤是讲解顺序，不是每个请求必须执行的 17 个步骤。** 一次请求根据路由选择分支；页面、人工后续事件和离线知识处理有自己的入口。整张图始终在同一画布，不需要在 8 张节点卡图之间切换。

先看中心上方的入口，往下到 N4 路由；再跟随选中路径：左侧电商事实 / 混合判断、中间 KF 原核心、右侧人工。主动申请进入下方确认链。所有聊天执行结果汇入 R，但 PAGE 结果直接回页面。再往下看反馈、知识构建、回归发布与新请求循环，最底部是存储和模型依赖。

实线表示处理与返回；长虚线表示异步事件；点虚线表示资源依赖 / 逻辑所有权。资源虚线不授予跨领域 SQL 权限。线条交叉不自动表示数据合并，按箭头端点及标签判断；相同收口的并入线共享通道。

## 图中应特别留意的边界

1. N4 顺序协调 N5 事实 → N6 政策证据 → N5 批准规则；不是 N5 直接调用 KF。
2. 咨询资格与发起申请分开。预检、明确确认、再次校验、幂等提交缺一不可；未知结果查原命令，不换键重办。
3. 页面申请共用 N5 守卫，但不制造 N4 Run / N3 聊天记录。聊天结果才进入 R。
4. 建单受理不等于接管。N3 确认 HUMAN 后才允许公开回复；已接管的客户新消息不再触发重新认领。
5. KF 保留 K1 直答、K3 FAQ 直出、K5 证据不足旁路，均回 K7。K7 的 end 仅是子调用完成，N3 正式保存后才有平台完成事件。
6. KF 诊断不回灌正式上下文；正式历史只来自 N3 授权快照。高风险回答先缓冲检查。
7. 反馈不直接修改在线库。知识修订也经过上传 / 校验 / READY、候选构建、独立回归和审批；失败返回修复或保留已验证版本。

示例中 O1001/L1、PF01、CMD01、AS001、P003/KB004 和 19900 分 CNY 均为虚构 DEMO。可申请、已提交、审核通过、退款到账是不同事实；政策示例不代表法律要求或真实商家承诺。

## 范围与验证

本版含 68 个处理 / 资源节点、85 条连线、17 个讲解区域。浏览器检查文字越界、节点重叠、连线穿框、标签盖住节点和重复 DOM ID；同时检查逐步定位、计数、缩放、资源开关、节点说明及离线无网络请求。还进行了静态业务语义复核，重点覆盖 PAGE 返回、混合查询、人工消息、知识修订守卫、KF 旁路及正式发布。

源文件：[生成脚本](source/build_panorama.py)、[渲染与验证脚本](source/render_panorama.cjs)、[节点和连线清单](source/panorama-manifest.json)。先运行 `python build_panorama.py`，再运行 `node render_panorama.cjs <Playwright 模块路径> <仓库外 QA 目录>`；浏览器使用独立无头 Chrome，不读取个人配置。

这是 **V1 目标流程**，不是已运行系统。M00.1–M00.4 完成，93 条业务验收仍 NOT_RUN；本次不启动 M01.1，不修改参考电商项目、KF 核心或压缩包。图未画尽的故障、灾备、权限与质量门禁继续遵守 [标准 1.1](../../implementation-standards/v1/README.md)。[上一版节点详解](V1分层流程与示例.html) 仍可用于逐项查字段，但本全景图为推荐图示入口。

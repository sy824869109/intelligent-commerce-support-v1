# 03 接口、事件、幂等与失败恢复实施契约

版本 1.0 · 2026-09-06 · V1 目标契约；不是现有 API 清单，也不是运行实现。

关联阶段：M02、M03、M07–M13、M17。配套 [会话控制](01_会话状态_打断与人工接管.md)、[业务确认](02_混合业务决策_用户确认.md)、[验收矩阵](04_业务RAG安全与灾备_验收矩阵.md)。

## E-01 可信上下文、序列与数据类型

| 字段 | 来源与用途 |
|---|---|
| tenant_id / actor_id / roles | 由 N2 认证和领域授权确认；客户端字段只能作为候选，不能覆盖真实身份 |
| request_id / trace_id | 服务端校验或生成；trace 传播仅用于诊断，不是授权凭据 |
| conversation_id / message_id / run_id | 分别关联正式会话、消息和 N4 执行；跨会话引用需要再次授权 |
| workflow_id / workflow_version | N4 草稿与状态版本；修改材料、目标或操作使旧确认失效 |
| control_epoch / assignment_id | N3 发布控制及 N7 分配引用；用于 C-04/C-06，不能代替订单授权 |
| command_id / confirmation_id | 稳定业务命令与用户确认引用，不能随网络重试重新生成 |
| event_id / correlation_id / causation_id | 稳定领域事件、业务关联、直接原因引用；事件重投 event_id 不变 |
| aggregate_id / aggregate_version | 源领域对象与版本，用于防止旧状态覆盖；不是全局时钟 |
| message_seq / event_seq / token_seq | N3 正式消息顺序、可恢复通知顺序、单个 Run 内草稿片段顺序，三者不能混用 |

规范 ID 为不携带个人信息的不透明字符串；下文 `C001` 等仅为示例。时间采用带时区的 ISO 8601，服务端事件使用 UTC；业务适用时区单独记录。金额为最小货币单位整数或明确精度十进制字符串并携带币种，禁止浮点金额。版本是可比较的领域版本或不可变制品引用，不用显示名称替代。

内部调用需要可验证的服务身份、租户与发起人委托范围；不得把客户端提交的内部 Header 原样作为授权事实。后台任务只获得任务所需权限，日志和事件不复制访问令牌、身份证或完整支付信息。

模型、服务和存储端点由受控配置决定，不能由用户消息指定；采用外部模型或其他出网处理前必须明确允许的数据范围与授权。局域网可访问不等于允许把私密上下文自动发往公网。

## E-02 逻辑操作与统一返回

下表固定行为、责任与必要字段。正式 HTTP 路径、OpenAPI/JSON Schema 在 M02.3 起进入 `packages/contracts` 并生成文档；不可将本表误认为这些端点已可调用。

| 操作名 | 入口 / 所有者 | 必需输入或守卫 | 正常返回 |
|---|---|---|---|
| `conversation.create` | N2 → N3 | 认证、幂等键、可选业务候选引用 | conversation_id、mode、version |
| `message.send` | N2 → N3 → N4 | 会话权限、幂等键、文本/已授权附件 | 已保存用户 message_id、Run 接收状态或排队状态 |
| `conversation.snapshot` | N2 → N3 | 当前授权、分页游标 | 正式历史、控制状态、活动 Run、恢复通知游标 |
| `conversation.events` | N2 → N3 | 当前授权、恢复游标 | E-03 的 SSE 通知，不执行交易 |
| `run.cancel` | N2 → N3/N4 端口 | Run 归属、控制代次、幂等键 | 实际取消/已完成/已取代状态，不返回“业务已撤销” |
| `workflow.preflight` | N4 → N5 | 业务目标、必要槽位、授权上下文 | 资格/预检快照、资源/规则版本、需确认摘要 |
| `workflow.confirm` | N2 → N4 → N5 | confirmation_id、payload_hash、workflow_version、幂等键 | command_id、接收/执行状态及可查询引用 |
| `command.get` | N2 → N5，或 N4 内部端口 | command_id 和发起人/领域访问权限 | E-05 的权威业务命令状态 |
| `handoff.request` | N2 → N4 → N3/N7 | handoff_request_id、会话归属、原因 | 实际建单结果；未建成不能返回受理成功 |
| `ticket.claim` / `ticket.transfer` | N2 → N7 → N3 | assignment/工单版本、客服权限、幂等键 | 分配及接管激活进度，遵循 C-06 |
| `ticket.reply` | N2 → N7 | 有效分配、公开性、reply_id/幂等键 | 原稿保存凭据和投递状态；不是客户已读 |
| `knowledge.upload` | N2 → N6 | 文件策略、知识空间权限、幂等键 | 文件/任务 ID、候选处理状态 |
| `knowledge.publish` / `knowledge.revoke` | N2 → N6 | 审批权限、目标版本、预期活动版本、幂等键 | 实际版本切换/撤回结果与审计 |
| `feedback.create` | N2 → N3 | 正式消息引用、会话权限、评价/原因、幂等键 | 原始评价记录 ID |

创建正式记录可返回 HTTP 201；已受理但未完成返回 202；读取和已有结果返回 200。202 不得被 UI 映射为“业务完成”。业务上不符合资格是明确结果，不必伪装成服务器 500。

成功返回示例（合成数据）：

```json
{
  "request_id": "REQ001",
  "trace_id": "TR001",
  "data": {
    "command_id": "CMD001",
    "command_status": "ACCEPTED",
    "business_id": null,
    "next_action": "QUERY_COMMAND"
  }
}
```

内部模块协议与浏览器协议分别版本化；KF 使用兼容包装转换，不强迫 KF 内部事件改成平台事件。

## E-03 SSE、WebSocket、正式消息与重连

沿用既有技术基线：AI 单向输出 SSE 优先，双向客服协作按需要使用 WebSocket；写操作仍通过明确的受权命令完成。KF 原有 WebSocket/生成器事件保留在兼容边界内。

| 平台事件 | 必要语义 | 持久性 / 对应关系 |
|---|---|---|
| `run.started` | Run 已获处理资格，不是业务已完成 | 可恢复通知，携带 run_id / epoch |
| `run.progress` | 可公开的处理进度 | 可丢弃的临时通知，不能包含私密诊断 |
| `answer.delta` | 草稿片段，带 Run、epoch、token_seq | 允许有限缓存，不保证逐 token 持久化 |
| `message.committed` | N3 已保存正式消息，带 message_id / message_seq | 必须可通过正式历史恢复 |
| `run.completed` | 本轮正式结果已保存，带 final_message_id | 仅在 N3 保存成功后发布；对应结果可查询 |
| `run.failed` | 本轮失败/超时等终态，带原因与可执行下一步 | 不得附带 success=true；业务命令可能仍需对账 |
| `control.changed` | 机器人/人工控制代次变化 | N3 持久状态，可恢复；客户端废止旧 Run 片段 |
| `resync_required` | 当前游标过期、片段缺失或缓冲无法恢复 | 客户端读取 snapshot/正式消息，不重新执行用户命令 |

1. 可恢复事件的 SSE `id` 是 N3 定义的不透明通知游标，与 Redis Stream ID、message_seq 和 token_seq 分离。重连使用 `Last-Event-ID` 或经校验的显式恢复游标。
2. delta 不设置新的持久 SSE id；丢失片段时可用短期缓冲补齐，否则清除不完整草稿并进入 snapshot/最终消息补查。不能因缺 token 自动重新生成或重新提交业务。
3. N3 在正式消息及其通知记录的本地事务中保存可恢复状态。Redis 丢失只影响临时投递/缓存，不丢失正式消息事实。
4. N4 已完成但 N3 保存失败：不发送 run.completed。保存成功但通知或响应丢失：查询并重新投递同一正式结果，前端按 message_id 去重。
5. 每次连接、重连、资源读取均重新授权；长连接有身份过期/撤销处理。私密与公开事件不得混在一个未经权限过滤的广播频道。
6. Cookie 模式需同源、Secure/HttpOnly、适当 SameSite，并对写操作落实 CSRF；Bearer 模式使用支持受控 Header 的客户端。原生 EventSource 不支持任意自定义请求 Header；不能因此把长期访问令牌放进 URL。最终会话方式由 M03 冻结。
7. Nginx 对流式响应避免代理缓冲，设置可观测超时和心跳；客户端有有界重连退避。传输断开与业务取消严格分离。
8. 有限缓冲和慢客户端处理必须有上限；超限时发起重同步或断开，不允许无限内存增长。SSE 与 WS 适配器遵守同一授权和去重语义。

SSE 示例：一个已保存的正式消息通知，而不是任意 KF end 的转发。

```text
id: cursor-demo-00017
event: message.committed
data: {"conversation_id":"C001","run_id":"R001","message_id":"M002","message_seq":2,"control_epoch":4}

```

SSE 的事件 ID 与重连语义参考 [WHATWG Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html)；本项目的持久消息和业务幂等由应用实现，不由 SSE 自动提供。

## E-04 请求幂等与并发约束

写操作必须接收稳定 Idempotency-Key，作用域至少为 `(tenant_id, initiating_actor_id, operation, target_scope, idempotency_key)`，并保存规范化 payload_hash、状态与结果引用。代理/Worker 重试保留原发起人和命令身份，服务账号不是新业务发起人。

| 重复情形 | 处理 |
|---|---|
| 同一作用域、同键、同载荷，已完成 | 返回原结果，不重复执行；返回前再次校验调用者当前权限 |
| 同键但载荷不同 | HTTP 409 `IDEMPOTENCY_CONFLICT`，不得覆盖原请求 |
| 同键同载荷，仍处理或对账中 | 返回原 command_id 与当前状态，不并行启动新命令 |
| 用户换新键重复申请同一商品数量 | 由 N5 业务规则、唯一约束及数量并发控制判断，不只靠幂等表 |
| expected_version 已过期 | 返回 `VERSION_CONFLICT`，重新读取/预检；不自动覆盖 |
| 记录到期后重投旧命令 | 依据持久 command_id、业务约束、审计/墓碑对账；不得默认视为新请求 |

幂等检查/占位与本领域写入需由唯一键和事务保证，不能用“先查没有，再插入”的无保护逻辑。长期外部调用使用可恢复命令记录，不保持数据库长事务。

幂等及去重记录的保留期必须覆盖最大重试、事件重放和灾备恢复窗口；删除策略不能仅按缓存 TTL 决定。值由发布档案冻结，敏感原文不应为幂等目的无限保留。

## E-05 业务命令状态与结果不确定

N5（其他写领域同理）的权威命令状态为：

| 状态 | 定义 | 下一步 |
|---|---|---|
| ACCEPTED | 命令记录已持久化，尚未开始领域执行 | 同 command_id 查询/处理 |
| EXECUTING | 已开始执行，不能按客户端断线认定未执行 | 等待有界 deadline；需要时对账 |
| SUCCEEDED | 已获知且记录确定的领域结果 | 返回业务 ID、实际状态、结果引用 |
| REJECTED | 前置条件/权限/确认/版本等不满足，没有执行该命令的业务效果 | 明确原因；重新预检/授权后可新发起 |
| FAILED | 已确认没有成功业务效果，失败原因确定 | 按错误策略处理；保留原命令与审计 |
| RECONCILING | 提交结果不明或上下游不一致，不能确认成功或无效果 | 查询本地/上游事实、人工处理；禁止换键盲重试 |

允许 `ACCEPTED → EXECUTING → SUCCEEDED / REJECTED / FAILED / RECONCILING`；接受后检查可直接 REJECTED；RECONCILING 依据证据转 SUCCEEDED/REJECTED/FAILED。终态内容不可被晚到失败响应覆盖；修正走新审计事件。

N4 调用超时无法确定 N5 是否接受时，保存发起记录与 command_id，展示“结果确认中”，查询 N5；这个调用方观察状态不能凭空创建 N5 的权威结果。即使查询暂时 404，也需确认请求是否仍在投递/处理，不能立即换键再提交。

外部适配器必须记录上游请求标识、授权与实际结果；上游支持幂等时复用同键，支持查询时先查结果。不支持可靠查询/幂等且可能已产生副作用时，转人工对账，不盲目重发。V1 不因此开放自动资金动作。

## E-06 领域事件与 Outbox / Inbox

领域写入、审计与 Outbox 在生产者本地同一事务提交。数据库回滚不能对外发布该事件。Outbox Relay 只处理已提交记录；每次重投保留 event_id，可更新投递次数，不修改历史 payload。

领域事件示例（合成数据，内部事件，不直接暴露给浏览器）：

```json
{
  "event_id": "EV001",
  "event_type": "ticket.public_reply.created",
  "schema_version": 1,
  "producer": "ticket-service",
  "tenant_id": "TENANT_A",
  "aggregate_type": "ticket",
  "aggregate_id": "T001",
  "aggregate_version": 8,
  "occurred_at": "2026-09-06T04:00:00Z",
  "correlation_id": "C001",
  "causation_id": "CMD_REPLY001",
  "trace_id": "TR001",
  "payload": {
    "reply_id": "REPLY001",
    "conversation_id": "C001",
    "assignment_id": "ASSIGN001",
    "visibility": "PUBLIC",
    "content_ref": "REPLY001"
  }
}
```

### 消费与确认顺序

1. N8 验证来源、schema、tenant 和路由，只把受支持的事件传给允许的处理器；字段 `visibility=PUBLIC` 本身不是充分的授权证据。
2. 实际产生业务效果的领域消费者建立 Inbox 唯一键 `(consumer, tenant, event_id)`。Inbox 记录与该领域写入在同一事务中完成。
3. 对人工回复：N8 调用 N3，N3 验证 N7 原始公开回复及收件人权限，并事务保存 Inbox、正式消息和自身 Outbox；N8 收到持久结果后才确认源消息。
4. N3 成功但 RPC 响应丢失，N8 可用同 event_id 重试，N3 返回原 message_id。禁止 N8 在调用 N3 前标记“已消费完成”。
5. 未处理成功不提前 ACK。达到重试策略后进入持久的死信/隔离记录；确认源消息前，必须确保该失败已可恢复，不能丢弃。

### 顺序、重放与保留

- 同一聚合的状态变化按版本防止倒退；消息/命令序列需要顺序时按聚合组织消费。
- 订阅可能跳过内部备注等事件，因此 aggregate_version 不一定连续。快照类事件可拒绝旧版本并查询权威快照；依赖前驱的增量事件必须显式携带/校验前驱版本，缺失时补齐或对账，不能无限等待“本就未订阅”的事件。
- Redis 消费者失联后通过待处理消息检查与认领恢复；认领可能再次执行，不能替代 Inbox。认领不会强制停止旧 Worker，处理时间/心跳与认领阈值必须协调，所有效果仍受领域幂等保护。[Redis XAUTOCLAIM 文档](https://redis.io/docs/latest/commands/xautoclaim/)
- Relay 发布成功不等于消费完成；Outbox/归档保留窗口覆盖可接受的 Redis 数据丢失和恢复窗口。Redis 丢数据后从保留事件和领域状态重新投递，依赖幂等避免重复副作用。
- 队列裁剪与删除必须考虑未确认事件、活跃消费者和恢复窗口；不能仅按固定长度裁掉尚未处理的唯一副本。
- 重放使用原事件 ID，修正业务含义使用新事件 ID 并保留 causation。禁止伪造新 ID 将同一命令当新业务执行。

这是一种可恢复的至少一次投递设计，不宣称端到端 exactly-once。Outbox 仍需处理重复和顺序问题，参考 [AWS Outbox 设计注意事项](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)。本项目不因此引入 AWS 运行依赖。

## E-07 错误分类、重试与时间预算

| code | HTTP 建议 | 是否自动重试 | 客户端/调用方动作 |
|---|---|---|---|
| AUTH_REQUIRED | 401 | 否 | 重新认证，恢复时重新授权 |
| ACCESS_DENIED | 403 或隐藏资源存在性的 404 | 否 | 不暴露未授权资源；停止 |
| INPUT_INVALID | 422 | 否 | 修正输入或材料 |
| RATE_LIMITED | 429 | 有界 | 遵循 retry_after，不并发轰炸 |
| IDEMPOTENCY_CONFLICT | 409 | 否 | 查询原提交，纠正载荷；不覆盖 |
| VERSION_CONFLICT | 409 | 否 | 刷新事实并重新预检/确认 |
| CONFIRMATION_EXPIRED | 409 | 否 | 新确认摘要，不复用旧授权 |
| RUN_SUPERSEDED | 409 | 否 | 切到当前 Run/会话快照 |
| UPSTREAM_UNAVAILABLE | 503 | 只读/已证明安全的同键操作有界重试 | 显示不可用或确定性降级 |
| DEADLINE_EXCEEDED | 504 | 不对未知写操作盲重试 | 查 Run/command_id；必要时对账 |
| COMMAND_RESULT_UNKNOWN | 202（提交结果待确认）；查询接口用 200 返回已知状态 | 不重新发起业务 | 查询原命令 / 人工对账 |
| PUBLICATION_FAILED | 503 | 仅补偿同一结果发布 | 查询正式消息，不重复业务 |
| SCHEMA_UNSUPPORTED | 内部隔离；外部 422 | 否 | 隔离告警，升级/修正消费者后重放 |

统一错误示例：

```json
{
  "request_id": "REQ002",
  "trace_id": "TR002",
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "订单状态已变化，请重新核对申请信息。",
    "retryable": false,
    "client_action": "REFRESH_AND_RECONFIRM",
    "command_id": null
  }
}
```

`retryable` 只描述该操作在规定同键/无副作用条件下可否重试，不能被客户端理解为任意新建请求。错误不得返回堆栈、SQL、密钥、模型内部 Prompt 或他人标识。

结果未知但可跟踪的 202 返回 `data`，其中包含 command_id、`observation=RESULT_UNKNOWN`、reason_code 与 next_action；N4 不知道 N5 的权威状态时 command_status 为 null。N5 明确记录 RECONCILING 后才返回该权威状态。不要同时返回互相矛盾的成功结果与 error 对象；202 与 200 查询均不承诺业务成功。

单个请求传播总 deadline；子调用预算之和与重试不能无限超过总预算。配置包括模型/检索/领域超时、最大尝试数、退避与抖动、熔断恢复条件、队列最大处理时间、死信条件。在线交互、人工消息、索引和评测任务使用独立队列/并发配额，避免离线任务耗尽在线资源；数值在 M17 用目标硬件冻结。

## E-08 附件、原文与索引的跨存储状态

原文/附件建议状态：`PENDING_UPLOAD → VALIDATING → READY / REJECTED`，撤回时 `REVOKED → DELETING → DELETED`，失败保留明确错误与补偿进度。知识处理任务另有解析/切片/索引/评测状态，不把“对象上传成功”当“可检索”。

- 建立带 tenant、owner、用途和有效期的上传许可；限制体积、真实文件类型、解压/页数/OCR 预算。原始文件名不拼接为服务器路径。
- 若支持网络知识源，URL、重定向与解析后的目的地址必须受控，拒绝访问未授权的内部/元数据服务；不能通过用户 URL 绕过服务端访问策略。已配置的内部存储地址与用户导入 URL 分别管理。
- MinIO 对象写入与 MySQL 元数据不是跨存储原子事务。通过 staging 引用、状态守卫、哈希及补偿清理处理“对象成功、元数据失败”和相反情况。
- 病毒/危险内容及解析安全检查通过后才能标 READY。故障或检查缺失不能默认为安全通过。
- N3 附件与 N6 知识原文分别拥有元数据，跨模块只使用受权引用/有时效读取，不把桶内路径当通行证。
- 入库任务按 source_hash、解析配置和目标版本去重；重试不得产生重复生效片段。索引与模型维度不兼容必须失败并保留旧发布版本。
- 候选索引不接收线上正式查询；撤回先禁访问，删除/重建后由任务对账确认完成。

## E-09 故障恢复与对账责任

| 故障点 | 权威证据 / 负责人 | 恢复动作 |
|---|---|---|
| N5 成功，N4 超时 | N5 command/business 结果 | 同 command_id 查询，补 N4 状态与 N3 回复 |
| N3 成功，客户端未收到 | N3 正式消息与通知 | snapshot 或事件补投；前端去重 |
| N7 已分配，N3 接管未确认 | N7 assignment + N3 control 快照 | 同 assignment 重试/对账；未激活不新写公开回复 |
| Worker 效果已提交，ACK 丢失 | 目标领域 Inbox 与结果 | 重新认领，同 event_id 返回原结果再 ACK |
| Redis 丢失 | MySQL 正式事实、保留 Outbox/归档、处理凭据 | 重建投递，处理缺口，不能伪造已消费 |
| 原文/元数据不一致 | 所属领域元数据、对象哈希、任务状态 | 补写或隔离清理；未 READY 禁引用 |
| 新索引或配置发布失败 | 各领域版本、兼容关系和发布审计 | 保留/回退已验证组合，相关路径降级；重新评测 |
| 从旧备份恢复 | 数据库、对象清单、发布版本、外部权威状态 | 隔离流量，核对已发生的业务/外部副作用后再恢复写入，不能立即盲重放外部命令 |

对账任务的修改仍由领域 API/处理器执行。必须有告警、重试上限、人工归属和恢复完成证据；N8 不能为了修复直接改别人表。

## E-10 合同演进与交付

- 事件 `schema_version` 与 HTTP API 版本、知识版本、模型版本分开。新增可选字段可保持向后兼容；必填、含义或枚举变化须兼容测试及明确迁移方案。
- 未支持的新事件进入隔离记录并告警，不静默丢弃或“猜字段”执行。部署顺序优先支持新旧合同的消费者，再发布新生产者。
- 保留旧事件读取能力覆盖重放窗口。删除字段/消费者前证明没有不可恢复的积压和历史依赖。

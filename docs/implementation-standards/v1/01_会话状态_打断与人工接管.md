# 01 会话状态、打断与人工接管实施标准

版本 1.1 · 2026-09-06 · V1 实施约束，尚未实现或通过业务验收。

关联阶段：M07、M08、M12、M14、M15。上位边界、术语和未冻结参数见 [标准索引](README.md)。相关测试见 [验收矩阵](04_业务RAG安全与灾备_验收矩阵.md)。

## C-01 状态分离与唯一所有者

禁止用一个 `status` 同时表示“聊天结束、申请完成和工单关闭”。

| 对象 / 所有者 | 必须表达的字段 | 语义 |
|---|---|---|
| Conversation / N3 | `service_mode`、`control_epoch`、`active_run_id`、`active_ticket_id`、`assignment_id`、`version` | 当前会话发布控制快照；不决定售后资格 |
| Run / N4 | `execution_status`、`publication_status`、`run_id`、输入消息、控制 epoch、deadline、诊断 | 一次计算/执行及其对外发布是两件事 |
| Workflow / N4 | `workflow_id`、`workflow_version`、`stage`、槽位、确认引用、`command_id` | 对话收集和申请发起流程，不等于 N5 售后状态 |
| Business command / N5 | `command_id`、执行状态、业务 ID、结果、规则/资源版本 | 业务是否实际执行，以 N5 为准；详见 E-05 |
| Ticket / N7 | 工单状态、分配版本、公开回复、内部备注、SLA | 关闭工单不能直接修改售后、支付或退款状态 |

`control_epoch` 是 N3 单调递增的发布控制代次，`version` 用于会话记录并发更新；不得使用客户端时间戳决定先后。N4 和 N7 通过 N3 的受权操作更新快照，不能直接写会话表。

## C-02 会话控制状态与转换

V1 `service_mode` 枚举为 `AI`、`HANDOFF_PENDING`、`HUMAN`、`CLOSED`。

| 当前状态 | 条件 / 发起者 | 下一个状态 | 必须产生的效果 |
|---|---|---|---|
| 无会话 | 用户有权建立会话，N3 创建 | AI | 建立身份归属、版本和初始控制 epoch |
| AI | N4 判断明确人工或安全升级 | HANDOFF_PENDING | N3 递增 epoch、撤销旧 AI 发布资格；N4 发起幂等建单 |
| HANDOFF_PENDING | N7 有效分配已就绪，N3 接管更新成功 | HUMAN | 关联工单与 assignment，递增 epoch，发布控制变化 |
| HANDOFF_PENDING | 用户明确取消排队，且 N7 证实没有生效接管 | AI | N7 撤销待处理接管，N4 请求恢复，N3 CAS 更新；竞争失败不能显示取消成功 |
| HUMAN | N7 明确结束接管且用户愿意回到机器人 | AI | 撤销当前人工控制，递增 epoch；不自动恢复旧确认凭据 |
| HUMAN | N7 转派至另一客服 | HUMAN | 替换已验证 assignment，递增 epoch；旧客服不能再新建公开回复 |
| 任一非 CLOSED | 用户或有权人员结束会话 | CLOSED | 禁止新的自动生成；处理中业务命令继续按事实对账，不自动撤销 |
| CLOSED | 用户明确重开且有权访问 | AI 或 HANDOFF_PENDING | 由 N4 判断是否需人工，N3 执行；旧 epoch、Run、确认凭据不复用 |

未列出的转换必须拒绝或进入显式恢复操作。`HANDOFF_PENDING` 期间只允许确定性的进度、材料收集提示和必要安全提示，不自动发起新业务写命令。用户消息仍保存并提供给客服，不丢弃。

明确人工不能被低置信度拦回普通 FAQ；身份和访问权限检查始终先于业务路由。无权访问时，不为用户暴露订单或工单存在性。

## C-03 单次执行与正式发布

`execution_status`：`QUEUED → RUNNING → SUCCEEDED / FAILED / TIMED_OUT / CANCELLED / SUPERSEDED`；RUNNING 可先转 `CANCEL_REQUESTED`，随后依据实际处理结果进入终态。QUEUED 可直接取消或被取代。终态不被重试改回运行中；新的尝试使用新的 Run 并关联原 Run。

`publication_status`：`NOT_READY → PENDING → PUBLISHED / SUPPRESSED / FAILED`。计算失败需要展示错误时也可以创建可审计的终态通知；它不是成功答案。PENDING 的补偿或 FAILED → PENDING 的发布重试复用同一个 Run 和唯一消息键，并再次验证发布资格，不重新执行交易。SUPPRESSED 不自动重发。

- `SUCCEEDED` 仅说明编排计算或已知的领域调用结果已取得，不代表客户端已经收到回复。
- `PUBLISHED` 只在 N3 返回正式消息保存凭据后设置；确认响应丢失时，先查询 N3 再重试。
- 客户端断线不自动将 Run 判为失败；后台结果可保存，重连后补查。
- N5 命令已提交但回执超时，Run 可以记录调用超时，命令结果必须保持“不确定/对账中”，不能映射为“业务未执行”。
- KF 内部 `end` 只结束 KF 子链；平台 `run.completed` 受 N3 正式保存约束，见 E-03。

## C-04 并发消息与旧结果隔离

V1 默认每个会话最多一个可向客户发布的 AI Run，并最多一个处于交互收集/确认中的业务 Workflow。订单本身可有多个符合领域规则的售后单，不受此会话限制替代。

1. N3 先幂等保存新用户消息，通过短事务/CAS 更新控制 epoch 和活动 Run 预留标识；不能在数据库锁内等待 LLM。
2. N4 获取处理资格后确定新 Run；跨服务响应丢失按预留标识查询/补偿。预留失败显示等待或错误，不能启动两个可发布 Run。
3. 新一轮取代旧的普通生成时，未终结的旧 Run 标为 SUPERSEDED；已计算成功但尚未发布的旧结果只将 publication_status 设为 SUPPRESSED，不篡改执行终态。N3 通过活动 Run 与 epoch 拒绝其后续正式发布。
4. 正式消息保存时，N3 必须在同一个本地事务中核验发布资格、唯一键并写消息和 Outbox。
5. delta 发送前核对控制资格；出站流按会话串行组织控制变化。客户端也依据 Run/epoch 丢弃过期 delta。
6. 已发送的字节不可撤回，不得声称 epoch 能消除已发生的泄露。安全检查遵循 C-09。
7. 连续点击相同消息发送使用同一幂等键；有意发送的新消息使用新键，不能靠文本相同判断用户意图相同。

两个浏览器标签页都必须收到控制变化；UI 按钮禁用只是体验措施，服务器约束不可省略。

## C-05 打断、改意图与取消

| 用户操作 | 必须怎么处理 | 禁止行为 |
|---|---|---|
| 停止生成 | 停止/抑制本轮文本输出，返回 Run 实际状态 | 将“停止回答”当作撤销售后申请 |
| 收集材料时问一个普通问题 | N4 可暂停 Workflow 进行只读咨询，之后询问是否继续；业务槽位不被新问题覆盖 | 把“我看看政策”当成申请理由或确认 |
| “不退了，换货”且未发起业务命令 | 明确修改/取消原草稿，递增 workflow_version，清除原确认凭据，重新预检 | 继续使用退货的金额、商品行或确认凭据提交换货 |
| 请求第二个不同业务流程 | 让用户选择继续、暂停或终止当前流程；V1 不同时维护多个活动交互草稿 | 让同一短句同时推进两个确认流程 |
| 已确认并正在提交时取消 | 查询 command_id，必要时进入 N5 的独立撤销申请流程 | 承诺已经回滚一个结果不确定的写入 |
| 要求人工 | 按 C-02/C-06 处理，废止尚未使用的草稿确认凭据 | 等待当前 LLM 正常生成完毕再受理 |

确认所创建的持久命令发起记录是提交过程的一部分；一旦进入 SUBMITTING，就不能以本地 Workflow 取消表示领域操作已撤销。若 N5 尚未接受，可通过明确的命令取消接口协商；发生竞争仍以 N5 命令事实为准。

取消、超时和被新请求取代均需保留原因、原 Run、触发者、控制代次与时间；不得直接删除证据。

## C-06 人工受理与真正接管的握手

1. N4 生成稳定的 `handoff_request_id`，请求 N3 进入 HANDOFF_PENDING，再调用 N7 幂等创建或关联工单。
2. 只有 N7 返回有效 ticket_id 后，才能显示“工单已受理”。建单失败时保留可恢复状态，显示“尚未成功受理”，提供重试/留言入口；不能编造排队位置。
3. N7 原子检查认领权限、工单版本和唯一有效分配。双客服竞争只有一人成功。
4. N7 将 assignment 与接管更新提交给 N3；N3 以 expected_epoch/CAS 应用模式变化。N7 可记录 `activation_status=PENDING/ACTIVE/FAILED` 表示同步进度，这不是会话模式或售后状态。
5. N3 确认 HUMAN 后，客服台才能显示“已接管”并开放新公开回复。失败或响应丢失时按 assignment_id 查询并重试，不能新增另一份分配。
6. 转派、排队取消和重开也走版本化握手；过期重试不能重新覆盖较新的接管决定。持续失败进入对账与人工处理。

该流程是跨领域的幂等协作，不声称 N3/N7 跨服务事务原子提交。实际部署即使共用数据库，也不得跨表越界实现隐式事务。

## C-07 人工回复、私密备注与结束接管

- N7 保存公开回复前校验当前 assignment、角色、工单状态和公开性；本事务保存回复原稿、审计及 Outbox。
- Worker 只能将已提交的公开回复事件交给 N3。N3 以源 reply_id/event_id 去重，形成正式人工消息；N7 内部备注没有可投递给客户的公开事件。
- 转派前已合法提交、但延迟投递的公开回复仍是历史事实；验证原始提交凭据与当前收件人权限后投递，保留原客服署名。不能简单以旧 epoch 将其丢掉。
- 转派后旧客服的新写入必须被 N7 拒绝。重新把私密备注改成公开回复需要一次新的授权、确认与审计操作，不能只改事件字段。
- 工单关闭、人工退出和客户会话关闭是不同动作。未显式交还控制时，机器人不自动接着办理旧业务。
- 私密备注、内部 SLA、人员联系方式不进入模型面向客户的上下文。

## C-08 超时、断连、无人在线与重启

| 情况 | 必须保留 / 恢复的结果 |
|---|---|
| 客户断线 | 正式消息与业务结果继续以领域记录为准；重连按 E-03 补查，不自动再次提交 |
| Run 超过 deadline | 停止生成或禁止其晚到结果发布；领域命令另行对账 |
| 排队无客服 | 展示真实受理状态、服务时间或留言入口；SLA 计时继续，可升级；没有依据不得给精确预计等待时长 |
| 人工客户端离线 | N7 按配置保留/转派分配；不由网络连接断开直接决定退款或会话关闭 |
| N3/N4 重启 | 从持久状态恢复控制、Workflow、未决命令；不能因为 Redis 缓存为空而恢复成新 AI 会话 |
| 恢复会话时发现过期材料/状态变化 | 重新获取授权资源和预检；旧确认失效后必须重新确认 |

deadline、排队 SLA、草稿保留期和离线转派条件需要配置并在对应模块验收前冻结；过期清理必须保留必要审计和业务关联。

## C-09 流式发布与输出前安全

V1 使用“普通咨询允许受控流式，高风险回答延迟发布”的策略，不改变 KF 内部生成顺序。

1. 在检索、缓存使用、向模型发送上下文前校验租户、资源、知识范围与当前权限；先脱敏，再构建最小必要上下文。
2. 引用文档是证据数据，不是新的系统指令。上传内容、图片 OCR、检索片段和外部响应均可能携带注入内容。
3. 普通咨询的 delta 只表示草稿，不构成订单资格、金额或审批承诺；前端标注生成中。
4. 涉及敏感个人信息、资金/资格承诺、权限冲突或高风险政策解释时，外层只发布进度；缓冲 KF 结果，完成必要检查后再发布最终答案。不能把全量敏感文本先发出去再遮罩。
5. 生成后引用/置信检查不等于事实保证。证据不能支持结论时拒答、澄清或转人工；业务字段只能来自领域结果。
6. 前端禁用未经清理的 HTML，限制不安全链接、外部资源加载和富文本注入；不能因为来源是模型就使用任意 HTML 渲染。
7. 成功终态前，N3 幂等保存最终文本、合法来源引用、版本和关联信息；失败不得发送成功终态。流式不承诺每个 token 均持久化。

安全设计参考 [OWASP 提示注入防护](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)（核对日期 2026-09-06）；这些措施降低风险，不宣称能彻底消除提示注入。

## C-10 最小审计、实施与完成条件

控制变化记录：tenant、actor、conversation、Run/Workflow/ticket/assignment 引用、旧/新状态、epoch/version、原因码、request_id、trace_id、UTC 时间、结果。日志不复制完整附件或敏感文本。

实施任务必须交付状态枚举、转换守卫、唯一键/并发约束、公开操作合同、重启对账、界面状态映射以及 `AT-C*`、`AT-U*` 相关证据。静态图、状态枚举定义或演示成功一次均不能替代并发与故障测试。

## C-11 正式历史与 KF 诊断历史的隔离

N3 是对话上下文的权威来源，KF 自存历史不是另一条可自动合入的正式历史。参考实现会在 K7 调用 `history.add_turn`，并在 K2 调用 `history.get_context_messages`；只拦截浏览器发布不足以防止未发布答案再次进入模型。

1. N3 为一次 Run 创建授权上下文快照：绑定 tenant、actor、conversation、run_id、control_epoch、截止 message_seq、消息引用及授权版本。当前问题单独传递，不再作为上一轮历史重复注入。
2. 历史仅包含当前仍可访问的正式用户/助手/人工公开消息。排除未发布草稿、失败部分结果、SUPPRESSED 答案和内部备注；被取代 Run 的原始用户消息保留审计，但不得当作仍待执行的指令。历史是数据，不是当前操作授权。
3. N6 外层提供请求隔离的 History Adapter：`get_context_messages` 只返回该快照；`add_turn` 保留 KF 原有诊断写入语义，但写入绑定 tenant/run 的诊断域，不回灌下一轮上下文。调用顺序、检索和生成核心不改。
4. 禁止在进程共享 QAService 上临时替换 `self.history`。新平台包装层通过请求级服务实例或安全的依赖注入传入适配器；服务内部端口与会话映射不能由浏览器任意指定。M09.1 用 ADR/合同固定实现方式并验证核心行为。
5. 摘要必须绑定源正式消息及权限版本；源内容撤回/权限改变后，旧摘要和缓存先失效，再从可访问记录重建。不能只过滤最近消息却保留含旧秘密的摘要。
6. 普通知识发布可固定版本，安全撤销仍优先。调用模型前和发布前重新检查权限/控制；快照不可用时明确降级/失败，不能回退到未经筛选的 KF 历史。已发送字节无法追溯撤回。
7. N3 发布成功后，下一 Run 重新取得正式快照；N3 发布失败只重试同一结果的发布，不重跑 KF 或领域命令。诊断保留/删除沿用授权、保留期和审计策略。

验收：AT-C13、AT-R13、AT-R14、AT-S11；M07 定义快照合同，M09 验证适配与并发，不修改原 KF 参考目录。

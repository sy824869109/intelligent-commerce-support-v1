## A-01 结果状态、优先级与执行责任

本矩阵共 80 个用例，初始执行状态全部为 `NOT_RUN`，已执行数 0、通过数 0。静态文档检查通过不得改变这些计数。

测试状态：`NOT_RUN / PASS / FAIL / BLOCKED / NOT_APPLICABLE`。BLOCKED 必须写阻塞原因和负责人；NOT_APPLICABLE 必须关联获准的版本范围变更，不能用它跳过尚未实现的 V1 必需能力。

- P0：数据/权限/资金边界、重复副作用、关键状态和恢复正确性；发现失败即阻断相关模块与发布。
- P1：V1 承诺业务、质量、前端、性能和运维能力；完整 V1 发布前必须通过。
- P2：额外体验或容量优化；本矩阵核心用例不以 P2 降低既有 V1 完成定义。
- 每个用例验证 API/事件、数据库或权威服务结果、界面/消息和审计，不能只看 HTTP 200 或一张截图。

## A-02 合成数据与测试隔离

所有数据在隔离测试环境生成，不复制真实客户隐私、生产访问令牌或本地参考项目运行数据。故障注入仅针对测试实例，不能在开发者日常数据库或已开放服务上直接执行。

| 数据集 | 必须包含的组合 |
|---|---|
| 身份 | TENANT_A/B；A 内两个不同客户；普通客服、另一客服、知识管理员、无发布权限运营者、已撤销角色 |
| 订单 | 待付款、付款同步中、已发货、已签收、已关闭；商品行数量 2；两个包裹不同状态；同用户多单、他人订单 |
| 申请 | 无申请、已部分申请、待审核、已关闭；两个并发请求争用同一剩余数量 |
| 规则与时点 | 生效前、边界时刻、失效后；下单/签收两种 time_basis；店铺/商品/渠道不同规则、同优先级冲突 |
| 知识 | FAQ 精确命中、FAQ 检索直出、文档充分证据、无证据、过期/撤回、跨租户/私密文档、表格/扫描件 |
| 材料 | 合法照片/PDF、伪装扩展名、超限文件、解析失败、受控恶意内容、重复上传、他人附件引用 |
| 运行故障 | LLM/检索/业务超时、DB 提交前后故障、ACK 丢失、乱序/重复事件、缓存丢失、重连、慢客户端、进程重启 |
| 版本 | 已发布 KB_A、候选 KB_B、旧/新规则与 Prompt、兼容与不兼容模型/索引组合 |

合成订单金额和退款/政策条件仅用于测试，不是实际店铺政策。每个用例记录 fixture_version、随机种子、时钟控制方式及隔离资源；涉及时间边界不能依赖真实等待数日。

## A-11 质量与性能门禁定义

### 质量指标口径

| 指标 | 计算/判定方式 | 防止误判 |
|---|---|---|
| 检索 Recall@k | 在有标注可答证据的问题中，统计相关证据召回比例；冻结 k、分母和相关性标注 | 不混入无答案问题虚增/拉低分数 |
| 排序质量 | 固定查询集及相关等级下统计 MRR/NDCG 或已选指标 | 不在不同语料/过滤范围间直接比较 |
| 引用支持率 | 对可核验主张逐项判断引用是否真正支持结论 | “出现引用编号”不等于有证据支持 |
| 应答/拒答 | 分开统计可答问题误拒与不可答问题正确拒答 | 不用全部拒答换取表面安全高分 |
| 业务正确性 | 资格、金额、状态、确认和领域结果与合成权威事实一致 | 不能只评估回答语言流畅 |
| 权限与副作用 | 在本矩阵安全及并发用例中，未授权暴露、重复业务效果为 0 | 仅说明已测范围通过，不宣称系统不存在所有漏洞 |
| 闭环质量 | 责任域、修复版本、回归和独立验证齐全 | 点赞率、关闭工单率不能单独等同解决率 |

基础集按场景、权限、可答性和难度分层；独立验收集不用于逐题调参。先冻结语料、标注、规则、KB、模型 revision、Prompt、硬件及参数，再执行。LLM 可辅助评分，但高风险业务、安全、金额和重要引用结论必须有确定性断言或人工复核。

V1 先建立与 KF 参考基线可比较的结果；不能要求随机生成文本逐字相同。阈值由 M09/M13 质量基线和业务风险确定，必须在正式验收前批准冻结，不能看到结果后临时降低门槛。

## A-12 灾备演练步骤与证据

1. 冻结场景、授权与模拟数据；建立恢复点的数据库备份、MinIO 对象清单/哈希、配置和模型/索引/规则/Prompt 版本引用。凭据单独安全管理，不打进 Git 或报告附件。
2. 记录备份开始/完成、可恢复数据时间点及一致性方法；单有“最近备份时间”不能证明对象与元数据一致。
3. 在隔离环境停止测试进程或注入允许的故障，记录故障时刻、最后成功业务及外部效果标识，不操作真实资金渠道。
4. 恢复 MySQL 和对象，核验孤儿、缺件、版本与权限；恢复原文和元数据后重建可派生索引，检查候选/活动版本状态。
5. 对未决命令、Outbox/Inbox、人工分配与会话控制进行对账。恢复窗口晚于备份的外部事实先核对；确认安全前不开放写流量或盲重放。
6. 回归登录、订单读取、受控申请、KF 主/旁路、人工消息、反馈；计算实际可丢失窗口和恢复服务时间，与批准 RPO/RTO 对照。
7. 记录失败、人工步骤、修复和二次验证。只有备份文件存在、服务能启动或索引条数相同，均不足以判通过。

备份访问权限、完整性校验、保留/清理和恢复凭据可用性属于同一次演练。回滚不能恢复已经被撤销的访问权限；安全撤销需要单独对账应用。

## A-13 Bad Case 责任与关闭条件

原始会话/评价由 N3、客服原始纠错由 N7 持有；知识修复由 N6、路由修复由 N4、业务事实/适配修复由 N5、人工流程修复由 N7 负责。跨领域总工作项的唯一归属仍需在 M13 通过 ADR/合同确认，禁止无意让 N6 或 Worker 成为所有业务事实中心。

每个工作项至少关联：原始证据引用、权限范围、问题类型、责任域/人、严重度、涉及版本、修复提交/制品、回归用例、验证人及验证结果。

状态语义：`OPEN → TRIAGED → FIX_READY → VERIFIED → CLOSED`；失败退回处理，误报/重复必须有原因和关联。上传文档、提交代码或关闭客服工单都不直接等于 VERIFIED。对客户不展示内部归因、人员备注或未批准政策。

反馈不能直接触发线上规则/知识发布或模型训练。只有授权、脱敏、明确用途的数据可进入相应评测流程；发布继续经过知识与业务各自门禁。

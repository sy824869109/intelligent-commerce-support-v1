# 02 混合业务决策与用户确认实施标准

版本 1.0 · 2026-09-06 · V1 实施约束，尚未实现或通过业务验收。

关联阶段：M04–M06、M08–M11。配套 [会话控制](01_会话状态_打断与人工接管.md)、[接口及恢复契约](03_接口事件_幂等与失败恢复.md)、[验收矩阵](04_业务RAG安全与灾备_验收矩阵.md)。

## B-01 分流顺序与业务范围

N2 身份/访问控制检查先于所有业务；N4 的业务路由按下列顺序执行并记录命中规则，不允许 LLM 覆盖硬条件：

1. 安全事件、明确人工请求、当前 HUMAN / HANDOFF_PENDING 控制规则。
2. 当前 Workflow 的取消、修改、继续、确认或安全中断；不把任意新句子都当成当前槽位。
3. 检查意图冲突、必需实体与授权上下文；不足先澄清，禁止先执行写入再补确认。
4. 选择确定性只读、知识问答、混合判断或受控业务申请。
5. 对下游返回的证据不足、规则缺失、数据过期和依赖失败，继续澄清、降级或人工处理。

拒答、澄清与人工升级是合法结果，不要求所有问题必须自动解决。V1 不自动支付、扣款、退款、改价或产生未经批准的交易执行能力；流程中的售后写操作主要是受控申请及获准的工作流处理。

## B-02 标准决策输出

每次路由至少输出以下信息，N4 保存其来源与版本：

| 字段 | 要求 |
|---|---|
| `route` | `CLARIFY / COMMERCE_READ / KNOWLEDGE / MIXED / BUSINESS_COMMAND / HUMAN / REFUSE` |
| `decision_reason` | 稳定原因码及可审计规则 ID，不能只有一段自由文本 |
| `intent_candidates` | 候选与可用置信信息；规则直答可标“不适用”，不能伪造概率 |
| `missing_slots` | 待收集字段、作用域及可选候选；不能暴露他人订单 |
| `resource_refs` | 经校验的订单、商品行、包裹、申请等 ID；文本抽取只提供候选 |
| `required_permissions` | 需要的读/申请/审核权限；权限事实由 N2/领域验证 |
| `workflow_ref` | 存在时带 workflow_id/version/stage |
| `version_refs` | 路由规则、业务规则、KB、Prompt、模型等本次实际使用版本 |
| `next_action` | 查询、澄清、生成确认摘要、提交获准申请或人工；不是任意工具代码 |

没有统一可比的全链路“置信分”。意图分、召回分、重排分、证据充分性和生成后检查分别记录；不能因一个检索分高就跳过业务或权限校验。

## B-03 业务决策表

下表是 V1 实施覆盖索引，不宣称覆盖所有市场业务。每个新增场景必须按 B-10 扩展用例，不能落入万能 `other` 后直接执行。

| 场景 ID | 典型请求 | 首选路径 | 必须有的上下文 / 约束 | 返回边界 |
|---|---|---|---|---|
| SCN-01 | 商品规格、库存、价格 | N5 只读 | SKU、渠道、时点；价格/库存标数据时间 | 库存查询不等于库存预留，展示价不等于最终结算价 |
| SCN-02 | 我订单到哪了 | N5 只读 | 订单归属、包裹选择、轨迹更新时间 | 多包裹逐件展示，不把一个包裹状态套给整单 |
| SCN-03 | 已付款为什么还显示待付款 | N5 只读 / 人工 | 支付渠道回执、同步状态、最近查询时间 | 不建议重复付款；不能凭用户截图修改支付事实 |
| SCN-04 | 一般退换政策 / 开票说明 | N6 知识 | 店铺、商品类别、地区/渠道适用范围 | 只解释政策，不声称某单已获准 |
| SCN-05 | 我这一单还能退吗 | N5 → N6 → N5 → N4 | 订单、商品行、时点、适用政策与领域规则 | `ELIGIBLE / INELIGIBLE / REVIEW_REQUIRED / UNKNOWN`，与审批结果分开 |
| SCN-06 | 申请退货退款 / 仅退款 | N4 Workflow → N5 受控申请 | 商品行、数量、原因、材料、预检、确认 | 返回申请 ID 和实际状态；不返回虚构的退款成功 |
| SCN-07 | 换货 / 补发 / 维修 | N4 Workflow → N5 | 原订单、数量、履约方式、材料、确认 | 库存/替换商品变化需重新预检；未经真实渠道验证不承诺已发货 |
| SCN-08 | 取消订单 / 修改地址 | N5 状态预检 → 获准的申请或人工 | 当前发货状态、资源版本、必要地址、确认 | V1 未实现直接动作时只提交申请；地址最小化传递、脱敏显示 |
| SCN-09 | 少件 / 错发 / 签收争议 | N5 事实 + N6 说明 + 申请/人工 | 商品行、包裹、证据、争议类型 | 不因物流“签收”就否定用户争议；不由 LLM 判责 |
| SCN-10 | 价保 / 优惠 / 部分退款金额 | N5 规则 + N6 依据 | 商品行、实付明细、优惠分摊、政策时点 | 金额由领域规则计算，LLM 不计算或改写承诺金额 |
| SCN-11 | 发票查询 / 申请 / 抬头修正 | N5 查询或受控申请，N6 说明 | 订单归属、票据状态、必要税务字段、确认 | 返回票据事实或申请状态，不把“申请受理”称为“已开票” |
| SCN-12 | 转人工 / 投诉 / 重大争议 | N4 → N7 | 会话和相关业务引用、升级原因、权限 | 本轮受理和后续人工处理分离 |
| SCN-13 | 信息不足、政策冲突、无可用知识 | CLARIFY / HUMAN | 明确缺什么、已知事实及失败原因 | 不编造政策，也不把技术故障描述为“没有相关政策” |
| SCN-14 | 查询他人订单 / 要求泄露隐私 | REFUSE | 服务端归属与最小权限检查 | 统一不泄露存在性；记安全审计 |

对每个场景维护 `support_mode=LIVE / DEMO / HUMAN_ONLY / UNSUPPORTED`。演示数据必须在环境、界面与验收报告中可识别，不能算真实渠道验收通过；生产降级不能偷偷切换到演示结果。

## B-04 订单与政策组合判断

以“已签收十天还能退吗”为例，N4 按明确步骤组合，V1 不依靠 Agent 自主选择工具：

1. 校验订单候选归属，必要时让用户选择订单和商品行。
2. N5 返回事实快照：状态、签收/付款等相关时点、数量、商品类别、渠道、已有申请与资源版本。同步数据附 `observed_at`、上游来源和新鲜度状态。
3. N4 只把政策适用所需的最小业务属性交给 N6，不把身份证、完整地址、银行卡或不必要的订单明细发送给模型。
4. N6 在授权数据域内查找适用政策，输出政策引用、版本、适用条件和冲突信息；无法判定适用性时显式返回 UNKNOWN/REVIEW_REQUIRED 所需原因。
5. N5 使用经过审核的可执行规则与事实快照做资格判断。规则需关联政策依据，不能把模型临时抽取的自然语言自动变成生效规则。
6. N4 组合“已知事实＋适用依据＋资格结果＋下一步”，保留引用。资格判断不是最终审批，也不是业务执行。

过期事实、规则缺失、政策冲突或兼容版本缺失时，输出 `UNKNOWN` 或 `REVIEW_REQUIRED` 并说明补充项；不能默认有利或默认不利于客户。最终业务申请仍执行 B-06 的重新校验。

## B-05 知识适用性、版本与来源

政策元数据至少支持：tenant、店铺/渠道、商品类别或 SKU 范围、地区、`effective_from`、`effective_to`、`time_basis`、优先级、来源、审核/发布记录和撤回状态。

- `time_basis` 指依据下单、付款、签收或其他已批准业务时点判断；时区和边界包含关系必须在业务合同中明确，不能一律套当前时间。
- 平台、店铺、商品、活动政策的优先级由业务确认；本标准不自行制定法律或商业政策。
- 同一优先级有冲突时，不由 LLM 私自挑选；记录冲突，进入审核或明确不确定回复。
- 一次查询固定 KB/索引/模型相关版本，组合业务还记录 N5 rule_version 与 N4 router_version。N4 通过领域 API 确认兼容版本组合；缺少兼容依据不执行相关命令。
- N6 激活知识、N5 激活业务规则是各自领域操作；跨领域更新不声称原子发布。涉及共同变更时，在批准的兼容组合可用前保持该路径人工/只读降级。
- 当前权限撤销、文档紧急撤回和安全封禁优先于历史版本固定。缓存、引用打开、历史重放都需要当前授权检查。
- 缓存至少隔离 tenant、角色/可见范围、数据域、场景、知识/策略版本；涉及订单的结果还需业务资源及版本，不能仅按相似问题复用。
- 原文删除用可追踪的撤回/删除流程：先禁止访问，再清理派生索引/缓存/对象，并保留合规所需最小审计。引用失效应显示不可访问，不泄露缓存原文。

KF 的 API → QAService → 显式 Pipeline、K0–K7 和直答/FAQ/证据不足旁路不变。包装、元数据治理与领域组合不得赋予 KF 交易写权限。

## B-06 预检、确认与提交

必须采用“草稿 → 预检 → 明确确认 → 提交 → 查询实际结果”，不能把用户咨询当成操作授权。

### 确认凭据绑定内容

N4 持有会话确认记录，N5 或对应领域持有最终命令校验结果。确认记录包含：

- confirmation_id、actor/tenant、workflow_id/version、操作类型；
- 目标订单/商品行/数量，原因和已授权附件引用；
- 领域预检的资源版本、规则版本、可选金额及币种、必要材料摘要；
- 规范化 payload_hash、创建/失效时间、用户明确确认的时间与方式；
- 状态 `PENDING / CONFIRMED / EXPIRED / INVALIDATED / USED`，以及稳定 command_id 引用。

用户可见摘要与实际提交载荷必须来自同一规范化结构。金额用精确金额表示，不能使用二进制浮点或从自然语言答案二次解析；币种不得省略。

### 提交守卫

1. 校验确认属于当前 actor、tenant、Workflow 与操作，不接受客户端自造 `confirmed=true`。
2. “确认提交”按钮明确绑定 confirmation_id；自然语言确认只有在唯一待确认上下文且含义明确时可接受。模糊的“好”“看看”不能直接提交。
3. N4 在本地事务中消耗/绑定确认凭据并创建唯一的命令发起记录及可靠投递记录；再次提交返回同一个 command_id。
4. N5 接收受权命令后重新检查身份委托、归属、当前业务状态、库存/时点等条件、资源版本、材料、确认载荷与幂等键。
5. 条件变化导致用户可见结果变化时，原凭据 INVALIDATED，返回新预检和新确认要求；不得悄悄更改金额、数量或商品。
6. N5 事务保存获准的申请、命令结果、审计和 Outbox。外部渠道提交按 E-05/E-07 处理，不假设本地事务包含第三方。
7. 结果不确定时返回 command_id 和查询入口，不创建新键重试。业务结果已知但聊天保存失败，只补偿回复，不重做业务。

一般查询不需要业务确认；涉及有副作用的申请、修改、删除、审核或发布才使用对应确认/审批流程。不同岗位的审批权限必须区分，用户确认不能替代内部审核权限。

## B-07 多商品、多包裹、部分申请与异常证据

- 申请最小目标细化到商品行与数量；同一订单已申请部分数量后，剩余可申请数量由 N5 计算并用并发控制保护。
- 多包裹状态、物流异常及证据按包裹/商品行关联；“一件签收”不能推进全单签收判断。
- 优惠、运费、赠品和已退款金额从权威明细和批准规则计算；无法取得完整明细时只说明或人工审核。
- 用户上传的截图和照片是待核验材料，不自动视为支付/物流事实。附件权限、类型与处理状态见 E-08。
- 无轨迹、数据同步延迟、上游不可用、确实无订单是不同结果。缓存数据允许展示时必须标注时间和不确定性，不用陈旧快照执行敏感命令。
- 重复有效申请由业务唯一约束/数量规则防止；不能仅依靠请求幂等键，也不能简单禁止同一订单的所有后续合法申请。

## B-08 结果合同与用户措辞

结果必须区分以下维度，不使用一个 `success` 混淆：

| 维度 | 示例 | 不能推导出的结论 |
|---|---|---|
| 请求受理 | 命令已登记、队列已受理 | 业务已经执行 |
| 资格结果 | ELIGIBLE / INELIGIBLE / REVIEW_REQUIRED / UNKNOWN | 售后已经审批通过 |
| 业务结果 | 申请 AS001 为待审核 | 退款已经到账 |
| 工单结果 | T001 已关闭 | 关联售后已完成或客户满意 |
| 回复结果 | 正式消息已保存 | 客户已经看见或确认收到 |

输出结构至少包含 outcome、reason_code、已知事实及 observed_at、适用来源、资格结果（适用时）、command/business/ticket 引用、业务状态、next_action 和版本。N4 可改善语言，不得改写这些结构化字段的值或强度。

## B-09 失败与人工降级

| 原因 | 必须采取的动作 |
|---|---|
| 缺订单/商品行/原因 | 澄清或授权候选选择；不执行命令 |
| 权限不足 | 统一拒绝且不泄露存在性，不携带未授权事实进入 RAG |
| 规则缺失或政策冲突 | REVIEW_REQUIRED / UNKNOWN，附可用依据并转审核 |
| 知识无命中 | 明确信息不足，可提供人工；不等同于依赖故障 |
| 模型故障 | 保留可用的领域查询/确定性模板/人工入口，不伪装模型回答 |
| 业务提交结果未知 | 查询原 command_id、等待对账；不提示“重新申请试试” |
| 高风险争议 | 人工优先；自动规则用于安全升级，不用于模型判责或擅自资金动作 |

## B-10 实施与验收交付

每个场景任务必须提交：触发样例、route、必需槽位、权限、适用状态、读/写范围、确认摘要、幂等与并发约束、上游适配模式、错误码、人工出口、来源与审计，以及对应 `AT-B*`、`AT-R*`、`AT-S*` 用例证据。

新增市场场景先判断它是现有场景的新状态组合还是新能力；更新场景索引和验收矩阵后再实现。真实渠道、人工处理和演示能力分别登记，禁止用“全部业务都支持”的笼统描述替代明确边界。

# ADR-0001：模块化单仓与 KF 知识服务边界

- 状态：Accepted
- 日期：2026-09-05
- 决策者：项目团队
- 关联任务：M00.2、M00.3
- 取代：无
- 被取代：无

## 背景

新平台需要从零建设电商业务、三类前端、会话编排、人工工单和数据闭环，同时保留 KF RAG 的核心知识链路。首版主要在局域网部署，团队规模有限；过早拆成大量独立仓库和网络微服务会增加版本、调试和部署成本，而把所有职责混在单体中又会阻碍后续 Agent 与知识图谱演进。

## 决策驱动因素

- 保持 KF RAG 核心分层和行为，不修改参考项目；
- 让业务事实、知识事实、会话和人工工单具有明确所有者；
- 支持五人团队并行开发、统一测试和原子提交；
- V1 局域网部署足够简单，后续能按负载拆分；
- 平台依赖升级不能污染 KF 已验证运行环境。

## 决策

1. 使用一个 Git 仓库保存 `apps`、`packages`、`deploy`、`docs` 和跨模块 `tests`。
2. 代码按 API Gateway、Commerce、Conversation、Orchestration、Knowledge、Ticket、Worker 和三个前端划分逻辑边界。
3. V1 允许多个低负载模块合并部署，但禁止跨边界直接写表。
4. Knowledge Service 使用独立依赖锁和运行环境包装 KF RAG 核心链路；平台服务可使用自己的当前稳定依赖。
5. 跨服务写入通过明确 API 或 Transactional Outbox 事件；Worker 不成为事实来源。
6. Agent 和知识图谱通过新端口接入，不侵入 Commerce 或 KF RAG 内部规则。

## 备选方案

### 在原电商项目上继续修改

短期改动少，但历史结构会继续限制职责边界、测试、数据闭环和后续演进，因此不采用。

### 每个模块独立仓库和独立微服务

隔离最强，但 V1 会产生过高的 CI、版本、网络、部署和本地调试成本，因此暂不采用。

### 把 KF RAG 代码直接合入业务服务

部署看似简单，但会耦合模型依赖、知识索引与交易逻辑，也违反 KF 核心边界，因此不采用。

## 结果与影响

### 正面影响

- 所有模块在一个变更中可以同步更新合同、测试和文档。
- Knowledge Service 可以独立控制依赖、资源和升级节奏。
- 逻辑边界明确，后续可依据性能数据拆分部署。

### 负面影响与成本

- 需要自动化检查防止跨模块越界。
- 单仓 CI 需要按变更范围优化，避免全部任务重复运行。
- 合并部署时仍需维持逻辑数据所有权，开发纪律要求更高。

## 安全与数据影响

多租户和资源归属由服务端验证。Knowledge Service 不得修改交易事实；前端不得访问内部存储；跨服务调用需要身份、租户、关联 ID 和审计上下文。

## 运维与回滚

V1 通过 Docker Compose 管理部署单元。各服务和数据迁移必须能独立回滚；知识索引可以从原文与元数据重建。依赖升级使用独立锁文件回退。

## 验证方式

- 自动检查项目结构和禁止资产；
- M02 开始增加架构依赖与契约测试；
- M09 使用 Golden Set 验证 KF RAG 行为；
- M18 验证局域网部署、备份、恢复和完整数据闭环。

# 版本与发布策略

## 产品版本

平台采用统一语义化版本 `MAJOR.MINOR.PATCH`：

- `MAJOR`：出现需要协调迁移的破坏性产品、部署或数据兼容变化。
- `MINOR`：向后兼容的新业务能力。
- `PATCH`：向后兼容的缺陷、安全或性能修复。
- 开发版本使用 `0.y.z-dev.N`，候选发布使用 `x.y.z-rc.N`。

当前版本的唯一事实来源为根目录 `VERSION`。正式发布 `v1.0.0` 前，项目处于 `0.x` 开发阶段。

## 独立兼容版本

产品版本不替代下列独立版本：

- HTTP API 使用路径版本，例如 `/api/v1`；
- 异步事件包含 `schema_version`；
- 数据库迁移使用不可重复的 Alembic revision；
- Prompt、知识文档、索引、模型和 Golden Set 分别记录版本及哈希。

## 依赖版本

平台服务与 Knowledge Service 使用独立锁文件。所有直接和传递依赖、容器镜像、模型 revision 必须可复现；禁止 `latest` 和浮动主版本。

## 发布流程

1. 所有目标任务为 `DONE`，阶段 PR 的 CI 和审查通过。
2. 更新 `VERSION`、`CHANGELOG.md`、部署和回滚文档。
3. 运行单元、集成、契约、E2E、安全、性能和恢复门禁。
4. 从受保护的 `main` 创建带签名或受保护的 `vX.Y.Z` 标签。
5. 发布镜像、SBOM、迁移说明和 SHA-256，并执行局域网冒烟测试。
6. 发布失败时按代码、配置、迁移、索引和模型五类分别回滚。

## 分支与热修复

普通开发进入当前 `codex/v1-greenfield`，阶段完成后通过 PR 合入 `main`。生产热修复从对应发布标签或 `main` 创建专用分支，修复后同时回合活动开发线，禁止只修生产分支造成长期分叉。
